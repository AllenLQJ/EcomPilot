# EcomPilot 开发执行计划（36 小时，多 Agent 并行）

本文件是新会话的唯一启动依据。执行者（Claude，下称"统筹"）读完本文件和 `ecompilot_project_roadmap.md` 后，无需用户介入即可推进到交付。规格以路线图为准，本文件只规定怎么做。

## 0. 目标与范围

**交付物**：路线图中项目三 EcomPilot（C 端交易与导购系统）的全部模块，技术栈按文档：FastAPI、MySQL 8.0、A2A（:8011~8015）、MCP 工具层、SSE、`static/index.html` 前端。

**深度分级**（避免把占位说成完成）：

| 等级 | 含义 | 模块 |
|---|---|---|
| A 深实现 | 业务逻辑完整，验收用例自动化通过 | 订单与库存内核、报价、优惠券锁、模拟支付、取消、售后候选反查与确认、提交 Ops、退款执行与状态查询、对账脚本、JWT 与租户隔离、受控凑单算价 |
| B 可用实现 | 主路径可用，异常分支部分覆盖 | 5 个 A2A 代理、MCP 工具层、chat_service 意图路由与 SSE、前端聊天与候选订单卡片 |
| C 最小实现 | 能启动、能返回结构正确的结果 | 种草笔记生成、多图源回退、环境适配（天气可用固定数据）、前端购物车抽屉 |

**不在范围**：真实 NLU 模型、真实 EcomRAG、真实 EcomOps（LangGraph）。三者用桩服务代替，契约按路线图 4.2 节。真实支付通道不做。

## 4. 通用约束（写进每个任务单）

1. **金额**一律整型分（`*_cents`），禁止浮点。
2. **身份**只从 JWT 取 `user_id`、`tenant_id`，请求体里的同名字段一律忽略。
3. **幂等**：下单用 `idempotency_key`；退款用 `refund_idempotency_key`（唯一索引）；取消用 `WHERE status='STOCK_LOCKED'`。
4. **库存**：乐观锁 `version`，`rowcount==0` 是版本冲突（重试 3 次，退避 20/50/100ms，仍失败返回 503 `CONCURRENT_VERSION_CONFLICT`），**只有 `sellable_stock < qty` 才返回 422 `INSUFFICIENT_STOCK`**。
5. **测试库隔离**：所有测试通过 `ECOMPILOT_DB_NAME=ecompilot_test_<uuid8>` 建独立库，测试结束删除；严禁多个任务共用同一库。
6. **错误码**：统一见 `contracts/errors.md`，禁止自造。
7. **完成声明必须附证据**：每个任务提交时给出运行过的测试命令及输出摘要；不接受"应该可以"。
8. 不得改动 `contracts/` 与任务单列出范围之外的文件。

## 5. 阶段与任务矩阵

时间为相对开工的累计小时，供节奏控制，不是硬死线。

### W0 契约冻结与基线（0–3h，统筹独立完成）

1. `uv venv`、依赖清单、`deploy/docker-compose.yml`（MySQL 8.0:3307）。
2. `contracts/schema.sql`：按路线图 4.1 的 EcomPilot 侧实体（catalog_categories、products_sku、price_quotes、orders、order_items、user_coupons、refund_executions、user_session_memory、nlu_label_to_catalog_map）。
3. `contracts/openapi/pilot.yaml`：全部对外接口，含 `/api/v1/orders/create`、`/internal/v1/refunds/execute`、`/internal/v1/refunds/status`；`contracts/openapi/stubs.yaml`：NLU、RAG、Ops 桩接口，按路线图 4.2。
4. `contracts/errors.md`、`contracts/fixtures/seed.sql`（至少含：热水器 SKU、多店铺 SKU、15 件凑单池、满减规则、券）。
5. `pilot/core/`：配置、DB、JWT 校验依赖、测试 token 签发工具、测试库工厂 `conftest` 基础。
6. 自检：`docker compose up` 后 schema 与 seed 可导入，`pytest --collect-only` 通过。
7. **提交基线**（edit_worktree 要求已提交的 HEAD 与干净的跟踪文件）。

## 6. 任务流转与质量闸门

**派发**：每个任务单包含：目标、拥有的目录、禁止触碰的目录、引用的契约文件、第 4 节通用约束、完成标准与必须运行的命令。通过 `create_work_item`（一个任务一个工作项，写入验收标准），再 `submit_task`，`mode=edit_worktree`，`cwd=` 仓库根目录。等待用 `wait_for_task`，不要紧循环 `get_task`。

**评审**：任务成功后取 `get_result`，检查：
1. 变更文件是否都在所有权范围内；
2. 在该 worktree 里实际运行任务单要求的测试（不采信执行器自述）；
3. 与契约逐项对照。

**合并**：Hub 不自动合并。统筹在主工作区用 git 合并 `hub/<task_id>` 分支；每个波次结束再提交一次，保证下一批任务从新基线出发。

**测试与实现冲突的裁决**：先回查路线图与契约。
- 测试读错了规格 → 退回 Cursor 重写，不改实现；
- 实现违反规格 → 派 `rework` 给 Codex（或统筹自改）；
- 规格本身有歧义 → 统筹按"更保守、更符合第 4 节通用约束"的解释裁决，并在 `docs/决策记录.md` 记一行，供交付报告披露。

**返工上限**：同一任务返工 3 次仍失败，统筹接手自己实现；该模块降一级并在交付报告中说明。

**阻塞处理**：Hub 任务出现 `waiting_for_user`、`REMOTE_STATE_UNKNOWN` 或执行器认证失败，先 `reconcile_task` 或换执行器（`switch_executor`）；两个执行器都不可用时，统筹自行实现关键路径（A 级优先）。

## 7. 何时才允许打断用户

只有以下情况：
1. 需要用户本人完成的操作（登录、授权、付费）；
2. 需要安装改变系统状态的软件而无权限；
3. 规格出现统筹无法自行裁决的根本性矛盾；
4. 要对外发布内容（推送远端、创建 PR）——本计划默认**不推送**，只做本地提交。

其余一律自行决策并记录。
